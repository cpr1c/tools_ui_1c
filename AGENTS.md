# AGENTS.md — Универсальные инструменты 1С

## Язык и стек

- Код продукта — **1С:Предприятие (BSL)**, префикс всех объектов: `УИ_`
- Сборщик — **OneScript (oscript)**, зависимости в `packagedef`, установка: `opm install`
- Сайт документации — **Docusaurus 3** (TypeScript, npm) в `website/`
- Линтер — **bsl-language-server** (`.bsl-language-server.json`), maxLineLength=150

## Сборка (из корня)

```bash
oscript -encoding=utf-8 ./src/builder/build.os <команда>
```

**Порядок важен**: сначала `xml`, затем одна из `cfe`/`cf`/`epf`.
Команды: `xml` (конвертация EDT→формат конфигуратора), `cfe` (расширение), `cf` (конфигурация), `epf` (портативная), `tests` (расширения для модульных тестов), `ci` (CI-сборка).

Пути к инструментам — через опции `--platformSource`, `--edtSource` или переменные окружения `TOOLS_UI_1C_BUILDER_PLATFORM_PATH`, `TOOLS_UI_1C_BUILDER_EDT_PATH`.

## Ключевые каталоги

- `src/Инструменты/src/` — исходники подсистемы в формате EDT (XML-представление 1С)
- `src/Портативный/src/` — портативная версия (внешние обработки)
- `src/МодульныеТесты/src/` — расширение с тестами (YAxUnit); единственное место, где допустимы методы YAxUnit
- `src/builder/` — скрипты сборки на OneScript; entrypoint: `build.os`
- `website/` — сайт документации, команды: `npm start` / `npm run build`

## Переиспользование кода (обязательно)

Перед тем как писать новую процедуру или функцию, **сначала ищи уже существующую** — дублирование в этом репозитории недопустимо:

- поиск по `src/` по смыслу задачи (имя метода, его часть, характерные вызовы), а не только по точному имени;
- проверяй общие модули подсистемы (`УИ_ОбщегоНазначения`, `УИ_ОбщегоНазначенияКлиент`, `УИ_ОбщегоНазначенияКлиентСервер` и др.) — нужный метод, скорее всего, уже есть;
- нашёл подходящий — используй его как есть; почти подходящий — расширь/обобщи существующий (лишний параметр со значением по умолчанию), а не копируй рядом;
- новый метод пиши, только если существующие не подходят по смыслу или контракту; размещай его в общем модуле соответствующей ответственности, а не в новой «свалке»;
- в описании правки/PR укажи, какие существующие методы использованы.

## Независимость от БСП и внешних библиотек

Подсистема должна работать **самостоятельно**, без БСП и других внешних библиотек: всё необходимое содержится внутри неё.

- Не вызывай методы БСП (`ОбщегоНазначения`, `ОбщегоНазначенияКлиентСервер`, `СтроковыеФункцииКлиентСервер`, `Пользователи` и т.п.) — подсистема устанавливается в конфигурации без БСП.
- Нужен функционал, который есть только в БСП, — реализуй аналог в своём общем модуле `УИ_*` (при переносе чужого кода указывай источник и лицензию).
- Интеграция с БСП допустима только как необязательный слой (подключаемые команды, расширение, внешние обработки), но не как зависимость ядра подсистемы.
- При доработке существующего кода вызовы БСП в нём — дефект: заменяй на собственный аналог.
- Методы YAxUnit (`ЮТ*`, `ЮТТесты`, `ЮТФабрика` и т.п.) доступны **только** в расширении `МодульныеТесты` (`src/МодульныеТесты/`). В коде подсистемы, портативной версии и внешних обработок они запрещены — там нужен собственный аналог в `УИ_*`.

## CI и контроль качества

- GitHub Actions: сборка по push в `develop`, релизы — по созданию тега
- Модульные тесты (YAxUnit) — `.github/workflows/run-tests-pr.yml`: на PR из этого репозитория
- SonarQube на sonar.openbsl.ru (`sonar-project.properties`); анализ по push и PR
- bsl-language-server проверяет стиль (`.bsl-language-server.json`, `.editorconfig`), стандарт — [Соглашение о кодировании](https://cpr1c.github.io/code_style/); служебные теги: `todo|fixme|отладка|debug|КОНСТРУКТОР_`
- Сайт деплоится на GitHub Pages из ветки `develop` при изменении `website/`

## Разработка

- Основная ветка — `develop`, релизная — `master`
- Код разрабатывается в **1C:EDT**; для конфигуратора есть инструкция в `website/docs/contributing/setup-configurator.mdx`
- Тестов в репозитории нет; формат правок — issue → PR
